## 2. 当前结论

LarkixMaker 的管理端已经超过“静态原型”阶段，具备真实 CMS 的骨架能力：

- 服务端 Session 登录。
- 文章与项目新增、编辑、软删除、恢复、永久删除。
- 草稿/发布状态。
- 首页轮播字段。
- Markdown 文件导入和实时预览。
- 封面上传与图片库选择。
- 内容 JSON 导出。
- 管理端可读取 `/api/admin/health`，但 UI 尚未展示。

Agent 3 当前最主要的缺口不是“能不能保存内容”，而是“内容生产是否安全、可控、可批量、可回溯”。尤其是离开页面未保存提醒、自动草稿、列表检索筛选、批量发布/回收、图片库管理、管理端健康面板和操作审计，会直接影响长期维护效率和误操作风险。

## 5. P0 任务细化

### P0-1：离开页面未保存提醒

目标：防止管理员写完正文或改完封面后误关闭、刷新、退出或切换编辑对象导致内容丢失。

建议能力：

- 监听标题、摘要、标签、Markdown、封面、状态、项目扩展字段变化。
- 设置 `isDirty` 状态。
- `beforeunload` 拦截浏览器关闭/刷新。
- 点击“新建空白”“编辑其他内容”“退出登录”前提示。
- 保存成功、重置表单、加载已有内容后清空脏状态。

建议评分：96
原因：这是内容生产最基础的安全网，实施范围集中在 `admin/admin.js`，收益极高。

### P0-2：自动草稿到 localStorage

目标：即使浏览器崩溃、Session 过期或上传/保存失败，管理员也能找回未入库内容。

建议能力：

- 每隔 5-10 秒或输入停止后自动保存当前表单快照到 `localStorage`。
- 草稿键按内容类型和编辑 ID 区分；新建内容使用临时 ID。
- 页面加载时检测未恢复草稿，并提示“恢复/丢弃”。
- UI 明确显示“本地草稿，尚未写入 SQLite”。
- 服务端保存成功后清除对应本地草稿。

建议评分：94
原因：当前内容一旦未点击保存就没有恢复路径；自动草稿能显著降低真实写作损耗。

### P0-3：全过程状态提示与按钮状态

目标：让管理员明确知道当前操作是否正在执行、是否成功、失败原因是什么，避免重复提交和误判。

建议能力：

- 保存、上传、导出、删除、恢复、永久删除时禁用对应按钮。
- 提供统一 notice/toast 区域，区分成功、警告、错误。
- 上传封面显示文件名、大小、进度感知文案。
- 保存成功后显示内容类型、标题、保存时间、状态。
- 请求失败时保留表单和本地草稿。

建议评分：91
原因：当前主要复用 `loginNotice`，反馈位置和语义都偏弱；这会直接影响 CMS 信任感。

## 6. P1 任务细化

### P1-1：内容列表搜索与筛选

目标：内容数量增长后仍可快速定位文章、项目、草稿、已发布内容和回收站内容。

建议能力：

- 搜索标题、摘要、标签、分类、项目状态。
- 按文章/项目筛选。
- 按草稿/已发布/回收站筛选。
- 显示当前筛选结果数量。
- 搜索条件保存在 URL hash 或 `localStorage`，刷新后保留。

建议评分：88
原因：内容超过十几篇后，当前单列表会迅速变慢、变乱。

### P1-2：批量操作

目标：减少重复点击，支持内容整理和集中发布。

建议能力：

- 列表项复选框。
- 批量发布、批量转草稿、批量移入回收站、批量恢复。
- 批量永久删除应保守处理，建议先不做或必须输入确认词。
- 若没有后端批量 API，可第一阶段前端顺序调用现有单项 API；第二阶段再与 Agent 2 协作做事务型批量 API。

建议评分：86
原因：批量发布和回收是 CMS 常规能力，但涉及误操作风险，必须和确认交互一起设计。

### P1-3：管理端健康面板

目标：管理员不离开后台即可看到当前版本、数据库、上传目录、公开内容数量等状态。

建议能力：

- 新增侧边栏入口“系统状态”。
- 展示 `/api/admin/health` 的版本、build、commit、数据库可用、上传目录可写、公开/管理端内容数量、上传数量。
- 异常项用醒目状态显示。
- 提供刷新按钮。

建议评分：84
原因：后端接口已经存在，前端接入成本低，能把运维信息带进内容工作流。

### P1-4：图片库管理

目标：让上传资源可整理，而不是只增不减。

建议能力：

- 显示文件大小、更新时间。
- 复制图片 URL。
- 删除未使用图片。
- 重命名图片。
- 删除前检查是否被文章/项目封面引用。

建议评分：82
原因：图片会长期增长，当前只有上传和选择，后续容易堆积和误选。

## 9. 当前风险提示

1. 当前管理端写接口依赖 Cookie Session，交接文档已指出 CSRF 防护缺口；这属于 Agent 2 和 Agent 3 的交界，Agent 3 做前端调用契约配合，Agent 2 做服务端防护更稳。
2. 当前 `savePost`、`saveProject` 对 payload 的服务端校验较弱，前端校验不能替代后端兜底。
3. 当前列表没有搜索筛选，内容增加后会降低维护效率。
4. 当前永久删除仅靠浏览器 `confirm`，误操作防护不足。
5. 当前图片库只支持上传和选择，不支持删除、重命名、引用检查，长期会造成资源混乱。
6. 当前阅读时长在管理端保存时固定为 `10 分钟阅读`，不利于内容质量表达。
7. 当前本地种子文件、SQLite、前台注入内容同时存在，生产事实来源应继续明确为 SQLite；管理端文案和导出功能应围绕这个原则设计。
