## 1. 当前项目判断

GokottaMaker 已从静态原型进入“真实可运行的个人技术站 + SQLite CMS”阶段。当前已经具备：

- Node.js 原生 HTTP 服务。
- SQLite 数据库存储。
- 管理端 Session 登录、CSRF、防误操作、软删除、恢复、永久删除。
- 文章/项目 CRUD、Markdown 导入、封面上传、图片库。
- 访客端首页、分类页、项目页、详情页、Markdown 渲染、Hero 轮播。
- RSS、Sitemap、Robots、健康检查。
- 腾讯云 Ubuntu + systemd + GitHub 部署链路。
- 回滚、备份、恢复、部署版本比对脚本。
- 初步模块化：`lib/db.js`、`lib/content.js`、`lib/auth.js`、`lib/audit.js`、`lib/validators.js`。
- 初步样式模块化：`styles/00-base.css`、`10-hero.css`、`20-content.css`、`30-accessibility-print.css`、`40-responsive.css`。

因此，下一阶段不应再把所有 Agent 同时拉满并行，而应按依赖顺序推进：先保证发布和数据安全，再整理后端接口，再稳定管理端，再扩大访客端体验，最后进入内容与 SEO 增长。

## 4. 新的执行顺序

建议从现在起采用顺序调度，不再默认同时开启所有 Agent：

1. Agent1 先确认生产更新、备份、回滚链路是否完全闭环。
2. Agent2 在稳定备份前提下继续拆后端接口，尤其是上传、SEO、静态服务和 API 回归。
3. Agent3 在后端接口稳定后收敛管理端编辑/内容列表/图片库体验。
4. Agent4 在管理端结构稳定后推进访客端视觉、响应式和阅读体验。
5. Agent5 在前台展示能力稳定后推进内容体系、SEO、文章计划和内链。

跨 Agent 改动必须写清输入、输出、影响文件和验证方式。

## 10. 跨 Agent 协作规则

### 数据来源原则

- 生产事实来源：SQLite。
- `data/posts.js` 和 `data/seed.js`：只作为初始化种子和开发兜底。
- 用户通过管理端编辑过的内容，不允许被种子同步覆盖。

### 图片原则

- 访客端和管理端都应优先使用内容自身 `cover`。
- 没有 `cover` 时按分类或项目类型兜底。
- 上传图片后，只有保存文章/项目才算正式引用。
- 后续需要 Agent2 建立引用关系，Agent3 提供清理入口，Agent4 保证展示稳定。

### 版本原则

- 代码变更完成后，如影响网站行为或页面，应更新：
  - `server.js` 的 `siteVersion/siteBuild`
  - `data/site-meta.js`
  - HTML 资源 query 参数
- 文档-only 变更不强制升级网站版本。

### 验证原则

最低验证：

```powershell
node --check admin\admin.js
node --check main.js
node --check post.js
node --experimental-sqlite --check server.js
```

服务验证：

```powershell
$env:PORT='临时端口'
$env:ADMIN_USERNAME='Gokotta'
$env:ADMIN_PASSWORD='管理员密码'
node --experimental-sqlite server.js
```

浏览器验证：

- 访客首页。
- 管理端登录。
- 编辑页。
- 内容列表。
- 系统状态。
- 文章/项目详情。
