## 2. Agent0 当前职能

Agent0 是本项目总控 Agent，核心职责是让多 Agent 协作保持同一方向、同一事实来源和同一发布节奏。

当前职责：

- 总控分工：把用户批注、测试报告、发布问题和产品想法拆成可执行任务，并分配给对应 Agent。
- 跨 Agent 协调：识别 Agent1 至 Agent20 的责任边界，避免重复修改、互相覆盖和职责漂移。
- 集成判断：确认不同 Agent 的改动是否可以并入同一发布批次，必要时拆分为视觉批次、运维批次、CMS 批次或内容批次。
- 验收收口：根据用户批注、Agent20 测试、脚本检查和页面复测判断 P0/P1 问题是否闭环。
- 风险确认：发布前确认 Git 状态、未提交改动、线上版本、回滚点、数据备份和用户侧代理问题。
- 交接维护：在 `docs/Agent0+总控与集成/` 中维护总控说明，在其他 Agent 目录中只写必要交接，不替代其长期职责。

Agent0 不直接长期接管：

- Agent1 的服务器运维、Nginx、HTTPS、systemd、发布回滚。
- Agent3 的 CMS 功能设计和管理端工作流细节。
- Agent4 / Agent7 的访客端视觉、品牌、动效和响应式体验细节。
- Agent5 的内容体系、SEO 文案和知识结构。
- Agent6 / Agent9 的小程序和 Markdown 渲染专项维护。

当用户要求“开始执行批注”时，Agent0 可以先处理跨模块整合和低风险修改，但长期应把可独立推进的任务交给对应 Agent。

## 3. 项目当前定位

LarkixMaker 是一个面向模拟电子、STM32、ESP32 和独立开源硬件项目的技术内容站，同时包含 CMS 管理端和网页小程序集合。

当前项目形态：

- Node.js 原生 HTTP 服务。
- SQLite 内容数据库。
- 访客端首页、品牌入口页、分类页、文章详情页、项目页、小程序中心。
- 管理端登录、文章/项目 CRUD、封面上传、Markdown 导入、轮播管理和页面排布工具。
- Markdown 渲染器、目录、代码块、公式降级和 DOCX 导出工具。
- LarkixElec 电路生成小程序和 MD2File Markdown 转换器。
- 腾讯云 Ubuntu 服务器部署，生产入口为 `www.larkix.com` / `larkix.com`。

当前技术基线：

- `package.json` 项目名：`larkixmaker`
- 当前包版本：`2.4.9`
- 启动命令：`node --experimental-sqlite server.js`
- 默认端口：`4173`
- 生产建议：Nginx 监听 `80/443`，反代到 `127.0.0.1:4173`
- 生产数据目录建议：`/srv/gokottamaker-data`
- 生产备份目录建议：`/srv/gokottamaker-backups`

## 6. 当前关键风险

Git 与工作区风险：

- 当前工作区存在大量未提交的前端、视觉、小程序和品牌相关改动。
- 当前已新增 Agent1 发布交接文档，尚未提交。
- 历史交接中曾出现 `main` 领先 `origin/main` 1 个提交的状态；本次确认时 `git status --short --branch` 未显示 ahead 标记。后续发布前必须以实时 `git status` 为准。
- 任何发布前都不能默认“全部改动都应发布”，必须先确认本次发布范围。

生产与访问风险：

- `www.larkix.com` 已能访问，但 HTTPS 仍需由 Agent1 确认 Certbot、Nginx 和续期。
- 浏览器“不安全”通常来自 HTTP 未启用 HTTPS。
- 曾出现命令行 curl 正常、浏览器 502 的情况，重点排查 Clash / Windows 系统代理 / 浏览器缓存。
- 根域名 `/` 当前是 Larkix 品牌入口页，完整内容站是 `/maker.html`。用户如果认为“网页显示不完全”，需先确认入口策略。
- 生产服务应只监听内网 `127.0.0.1:4173`，公网通过 Nginx `80/443` 进入，不建议继续暴露 `4173`。

协作风险：

- 视觉品牌、前端页面、CMS、发布链路已经交织，Agent0 必须先拆分责任再安排执行。
- Agent1 的发布稳定性任务优先级高于继续视觉微调。
- 多平台内容分发、微信公众号、小红书、Bilibili、抖音、知乎、CSDN 属于新功能架构，不应混入当前 HTTPS / 发布稳定性工作。

## 7. 后续执行原则

发布前原则：

- 先确认发布范围，再执行 Git add / commit / push。
- 先确认工作区是否混入无关视觉实验和未确认资产。
- 先跑本地检查，再交给 Agent1 发布。
- 生产改动前必须有备份和回滚点。

建议发布前检查：

```powershell
npm.cmd run check:version
npm.cmd run test:markdown
node --experimental-sqlite --check server.js
git diff --check
powershell -ExecutionPolicy Bypass -File scripts\verify-api.ps1
git status --short --branch
```

Agent0 分工原则：

- P0 运维故障先交 Agent1。
- 数据/API 合约交 Agent2。
- CMS 工作流交 Agent3。
- 访客端布局交 Agent4。
- 内容与 SEO 交 Agent5。
- 小程序交 Agent6。
- 品牌与视觉规范交 Agent7。
- 市场表达交 Agent8。
- Markdown 解析交 Agent9。
- 测试复核交 Agent20。

交接原则：

- 每次重大决策必须写入对应 Agent 目录。
- 每次发布必须有版本、commit、健康检查、备份目录和回滚说明。
- 文档必须写清楚“谁负责、改哪里、验收什么、不负责什么”。
- Agent0 保持总控视角，不把临时救火变成长期越界接管。
