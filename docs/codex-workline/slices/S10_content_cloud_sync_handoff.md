## backup_and_checksum_gates

- 包 checksum 必须是 64 位十六进制 SHA-256；shell 与 Node 导入进程各校验
  一次，防止两阶段之间包字节变化。
- apply 不接受只有备份目录或口头说明的证据，必须传入
  `backup-linux.sh` 生成的 `manifest.txt`。
- manifest 的 `source_dir` 必须与 apply `DATA_DIR` 解析到同一路径；
  `backup_dir` 必须与 manifest 所在目录相同。
- `source_database_integrity` 与 `backup_database_integrity` 只接受
  `ok`、`missing` 或 `skipped-sqlite3-missing`；其他结果阻断。
- 默认只接受 2 小时内的备份，可通过正数
  `CONTENT_SYNC_MAX_BACKUP_AGE_HOURS` 收紧或显式调整。
- `manifest.sha256` 缺失或为空时 apply 一律阻断；存在时必须全量通过。
- 校验和应在传输或发布前由验收方独立锁定；部署目标只做匹配，不应在同一
  apply 命令内现算新期望值。

## idempotency_evidence

隔离包取两条已验收计算书节点：

1. 首次 apply：`created=2, updated=0, unchanged=0`。
2. 同包同 checksum 重复 apply：`created=0, updated=0, unchanged=2`。
3. 只修改第一条节点标题并换用新 checksum：
   `created=0, updated=1, unchanged=1`。
4. 数据库核对保持第二条节点载荷不变，证明变化包只更新明确命中的稳定
   slug。

## failure_and_rollback_behavior

隔离 `DATA_DIR` 必须存在
`.larkix-content-sync-disposable` 标记，并同时设置
`CONTENT_SYNC_ALLOW_TEST_HOOK=true`，才允许故障注入；生产目录无法误用
该钩子。

在第一条节点保存后注入失败时：

- Node 导入进程非零退出；
- 外层 SQLite 事务回滚；
- 两条节点标题均保持故障包之前的 r2 值；
- shell 报告
  `Last safe checkpoint: backup_verified_checksum_locked`；
- 输出 `restore-linux.sh --dry-run` 和操作员批准后正式 restore 命令；
- 未自动恢复，未发起任何网络调用。

脚本同时提示：打开数据库可能先执行当前代码中的加法迁移；若需要数据库
整体回到导入前状态，应在停机和恢复范围确认后使用已校验备份。

## decisions

- 云端同步脚本设计为在目标主机本地执行，不在脚本中内置 SSH、SCP 或云
  凭据；包传输属于已验收发布链路，目标主机只按独立 checksum 验证。
- canonical 包保持 `draft + private` 语义；预览 override 不得成为正式同步
  输入。
- 稳定身份采用计算书包既有 `id=slug`，不另建映射表或修改应用 schema。
- 幂等判断只比较可同步业务字段；`deletedAt` 不在写入载荷中，因此同步不会
  静默恢复 Owner 已软删除的节点。
- 故障时只提供恢复命令，不自动执行破坏性 restore。
- `deploy-update.sh` 无内容包配置时保持原行为；有配置时也不能绕过既有备份
  和最终健康检查。
