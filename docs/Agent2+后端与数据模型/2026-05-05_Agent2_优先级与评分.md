## 2. 当前后端与数据模型结论

项目已经具备可运行的 Node 原生 HTTP + SQLite 后端，覆盖管理员登录、Session、内容 CRUD、软删除/恢复/硬删除、图片上传、内容导出、RSS、Sitemap、Robots、健康检查和静态资源服务。

但 Agent 2 负责的底层还处于“功能已集中实现，结构尚未工程化”的阶段。当前 `server.js` 约 840 行，包含数据库初始化、补列迁移、认证、数据读写、上传、SEO、健康检查、API 路由和静态文件服务。短期继续堆功能会让变更风险快速上升。

数据模型方面，当前生产模型仍以 `posts` 和 `projects` 两张内容表为核心，`tags`、`categories`、审计日志、正式迁移记录、时间语义和数据约束都还不完整。`data/posts.js` 和 `data/seed.js` 仍承担初始种子职责，SQLite 应逐步明确为生产事实来源。

安全方面，已经有 scrypt 密码哈希、HttpOnly Cookie、SameSite=Lax、登录失败限流和上传类型/大小限制；但管理端写接口仍缺少 CSRF Token 或等价的双提交/自定义请求头校验，缺少操作审计，写入 payload 校验也偏弱。

## 6. P0 任务细化

### P0-1：管理端写接口 CSRF 防护

目标：保护依赖 Cookie Session 的管理端写操作，避免管理员登录状态下被第三方页面诱导提交写请求。

建议能力：

- 登录成功后生成服务端 CSRF token，或通过双提交 Cookie + 自定义 header 校验。
- 管理端 `fetch` 统一携带 `X-CSRF-Token`。
- 所有写接口校验：`POST /api/logout`、`POST /api/posts`、`POST /api/projects`、`POST /api/uploads`、恢复、删除、硬删除。
- `GET /api/session` 可返回 token 或提供独立 `GET /api/csrf`。
- 保留 SameSite=Lax，但不要只依赖 SameSite。

评分：97
原因：这是当前管理端写接口最直接的安全缺口，且实现范围清晰、收益高。

### P0-2：正式数据库迁移机制

目标：从启动时散落的 `ensureColumn` 升级为可追踪、可复盘、可验证的迁移系统。

建议能力：

- 新增 `schema_migrations` 表，记录已执行迁移版本、名称、执行时间。
- 新建 `migrations/001_initial.sql`、`002_content_status_fields.sql` 等。
- 启动时按顺序执行未完成迁移，失败即中止启动并输出清晰错误。
- 每个迁移保持幂等或由 `schema_migrations` 控制只执行一次。
- 迁移前建议 Agent 1 配合备份，但迁移逻辑本身由 Agent 2 负责。

评分：95
原因：后续 tags、categories、audit_logs、时间字段都会依赖迁移机制；没有迁移层，数据模型越改越难控。

### P0-3：操作审计表 `audit_logs`

目标：记录管理员对内容和上传的关键写操作，方便追踪误删、恢复、发布、覆盖和上传行为。

建议表结构：

```sql
CREATE TABLE audit_logs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  actor_user_id INTEGER,
  actor_username TEXT,
  action TEXT NOT NULL,
  entity_type TEXT NOT NULL,
  entity_id TEXT,
  metadata_json TEXT,
  ip_address TEXT,
  user_agent TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

建议覆盖动作：

- `login_success`、`login_failed`、`logout`
- `post_save`、`project_save`
- `post_soft_delete`、`project_soft_delete`
- `post_restore`、`project_restore`
- `post_hard_delete`、`project_hard_delete`
- `upload_create`
- `content_export`

评分：92
原因：当前管理端已能永久删除内容，但没有行为记录。审计是内容生产进入长期维护前必须补上的底座。

### P0-4：拆分数据库与内容读写层

目标：先拆最稳定、收益最高的底层边界，降低 `server.js` 继续膨胀的风险。

建议第一批拆分：

```text
lib/db.js       数据库路径、连接、迁移、初始化、事务辅助
lib/content.js  posts/projects 查询、保存、删除、恢复
lib/auth.js     密码、Session、当前用户、CSRF
```

暂不建议第一步就大规模拆分所有模块。先把数据库和内容层抽出，能直接支撑迁移、审计、校验和后续 Agent 3 的 CMS 工作。

评分：90
原因：架构收益高，但要注意分批落地，避免一次性重排导致行为回归。

## 7. P1 任务细化

### P1-1：API payload 校验与规范化

当前 `savePost`、`saveProject` 对必填字段、枚举值、slug/id 格式、URL、数字范围、字符串长度校验不足。建议新增轻量校验层：

- `id/slug` 只允许稳定 URL 字符。
- `publishStatus/visibilityStatus/statusKey/categoryKey` 使用白名单。
- `featuredOrder/progress/stars` 做范围限制。
- `markdown/title` 必填并限制最大长度。
- `cover/repoUrl/bomUrl/docsUrl` 做路径或 URL 规范化。

评分：88。

### P1-2：内容时间字段补齐

建议为 `posts/projects` 统一补齐：

- `created_at`
- `updated_at`
- `published_at`
- `deleted_at`

当前 `date` 更像内容展示日期，不应同时承担创建、发布、排序和 SEO 语义。

评分：86。

### P1-3：正式 tags/categories 模型

建议先兼容旧字段，再逐步迁移：

- 保留 `posts.tags` 和 `projects.tags` 作为兼容输出。
- 新建 `tags`、`post_tags`、`project_tags`。
- 新建 `categories`，短期继续输出 `category` 和 `categoryKey` 给前台。
- API 输出保持现有契约，内部模型先升级。

评分：84 和 81。

## 10. 当前风险提示

1. `server.js` 单文件职责过多，继续添加后端功能会放大回归风险。
2. 当前数据库迁移没有版本记录，无法回答“生产库已执行到哪一步”。
3. 管理端写接口依赖 Cookie Session，缺少 CSRF 防护。
4. 永久删除、恢复、上传、导出等关键操作没有审计记录。
5. `tags` 仍是文本字段，不利于筛选、SEO 聚合和长期内容体系。
6. `date`、`updated_at` 的语义不够清晰，发布排序和 SEO 时间可能混用。
7. 静态种子与 SQLite 同时存在，需要明确生产事实来源，避免未来覆盖真实内容。
8. 本地数据库主文件直接读取时仍显示基础字段，新增字段依赖服务启动补列；迁移机制完成前，生产变更应格外谨慎。
