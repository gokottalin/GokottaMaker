# Agent2：数据安全审计与备份恢复优化清单

时间：2026-05-10  
角色：Agent2 后端与数据模型  
目标：在开始持续写新文章前，确认数据安全底座，并列出值得优先优化的备份与恢复项目。

## 1. 总体结论

当前项目已经具备基础数据安全能力，可以开始写新文章，但还没有达到“误保存、误删、整机故障都能从容恢复”的高可靠状态。

当前已具备：

- SQLite 生产数据独立于代码目录，云端使用 `/srv/gokottamaker-data/database/gokottamaker.sqlite`。
- 上传图片独立持久化，云端使用 `/srv/gokottamaker-data/uploads`。
- Linux 备份脚本会备份 `database/` 和 `uploads/`。
- 有 `manifest.txt` 与 `manifest.sha256`。
- 服务器已安装 `sqlite3` 后，备份数据库完整性可校验为 `ok`。
- 恢复脚本会先校验备份，再停止服务、创建安全副本、替换数据、启动服务。
- 内容删除默认是软删除，支持从回收站恢复。
- 管理端写接口已有登录、CSRF、校验与审计日志。

主要不足：

- 备份仍主要在同一台 VPS 本地，服务器磁盘丢失时风险较高。
- 文章没有版本历史，误保存会覆盖正文，只能通过整库备份或手工抽取旧行恢复。
- 保存文章与标签同步、审计日志不是同一个事务，极端情况下可能出现部分写入。
- 永久删除接口仍存在，生产环境误点后只能依赖备份。
- 本地 Windows 备份脚本不具备 Linux 备份脚本同等级的 SQLite 一致性校验。

## 3. 当前恢复方式

### 3.1 写文章前手动备份

建议在开始大篇幅写作、批量上传图片、发布前执行一次：

```bash
cd /opt/GokottaMaker
sudo bash scripts/backup-linux.sh /srv/gokottamaker-data /srv/gokottamaker-backups
LATEST="$(ls -1dt /srv/gokottamaker-backups/* | head -n1)"
cat "$LATEST/manifest.txt"
```

关键字段应为：

```text
source_database_integrity=ok
backup_database_integrity=ok
source_uploads_files=...
backup_uploads_files=...
```

### 3.2 恢复前 dry-run

必须使用显式 `--dry-run`，不要再使用 `DRY_RUN=true sudo ...`，因为 sudo 可能丢弃环境变量。

```bash
cd /opt/GokottaMaker
LATEST="$(ls -1dt /srv/gokottamaker-backups/* | head -n1)"
sudo bash scripts/restore-linux.sh --dry-run "$LATEST"
```

### 3.3 正式恢复

```bash
cd /opt/GokottaMaker
sudo bash scripts/restore-linux.sh /srv/gokottamaker-backups/YYYY-MM-DD_HH-MM-SS
curl -fsS http://127.0.0.1:4173/healthz
```

恢复脚本会创建安全副本：

```text
/srv/gokottamaker-data.before-restore-YYYY-MM-DD_HH-MM
```

### 3.4 代码回滚

代码回滚不替换数据：

```bash
cd /opt/GokottaMaker
bash scripts/rollback.sh <commit>
```

如是数据误写、误删、图片丢失，应使用恢复脚本，不应只做代码回滚。

## 4. P0 优化项

| 优先级 | 项目 | 评分 | 原因 | 建议 |
|---|---|---:|---|---|
| P0 | 增加文章/项目版本历史 | 96 | 当前保存会覆盖正文，误保存只能靠整库备份恢复 | 新增 `content_revisions` 表，每次保存前记录旧版本，管理端提供单篇恢复 |
| P0 | 建立异地备份 | 95 | 备份与数据在同一 VPS，磁盘丢失或主机故障会同时丢失 | 使用对象存储、另一台服务器或私有备份仓库同步 `/srv/gokottamaker-backups` |
| P0 | 生产环境禁用永久删除 | 92 | `hard delete` 会真实删除行，误点后只能依赖备份 | 增加 `ALLOW_HARD_DELETE=false` 默认关闭；仅软删除和恢复 |
| P0 | 保存内容使用事务 | 90 | `savePost/saveProject` 与 `syncTags` 分开执行，极端情况下可能部分写入 | 将内容保存、标签同步、审计日志放入同一事务 |
| P0 | 备份新鲜度告警 | 88 | 写作前需要知道最近备份是否可靠 | `/api/admin/health` 增加最近备份年龄；超过 26 小时或校验缺失时管理端红色提醒 |

## 7. 推荐推进顺序

第一步先做 P0-1、P0-2、P0-3：

1. 增加文章版本历史。
2. 建立异地备份。
3. 禁用生产永久删除。

这三项直接覆盖“误保存、整机丢失、误删”三类最大风险。

第二步做 P0-4、P0-5：

1. 保存内容事务化。
2. 管理端显示备份新鲜度告警。

这两项能让日常写作更稳，也能减少隐藏的半写入问题。

第三步做 P1：

1. 修正文档 dry-run 命令。
2. 增强本地备份脚本。
3. 增加备份巡检脚本。
4. 发布前强制校验备份。

## 8. 写新文章前的最低安全流程

每次准备写重要文章前：

```bash
cd /opt/GokottaMaker
sudo bash scripts/backup-linux.sh /srv/gokottamaker-data /srv/gokottamaker-backups
LATEST="$(ls -1dt /srv/gokottamaker-backups/* | head -n1)"
cat "$LATEST/manifest.txt"
sudo bash scripts/restore-linux.sh --dry-run "$LATEST"
```

如果看到：

```text
source_database_integrity=ok
backup_database_integrity=ok
Backup validation passed. SQLite integrity: ok
Dry run completed. No files changed.
```

再开始写作。

当前可用，但建议尽快进入 P0 优化，尤其是“文章版本历史”和“异地备份”。这两项完成后，写作时的心理负担会明显下降。
