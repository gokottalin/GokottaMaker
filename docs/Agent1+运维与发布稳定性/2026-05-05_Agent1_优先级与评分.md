## 2. 当前结论

GokottaMaker 目前已经具备基础部署、systemd 托管、数据备份、恢复和健康检查能力，但 Agent 1 负责的“发布稳定性闭环”还没有完全形成。

当前最主要的缺口是：

1. 没有独立回滚脚本，部署失败后的恢复路径依赖人工判断。
2. 备份脚本只复制数据，没有 manifest、校验和、SQLite 完整性验证和恢复前校验。
3. 部署脚本会输出本地和远端 commit，但没有部署前后版本、build、健康状态、数据状态的结构化对比。
4. `/healthz` 已包含版本、commit、数据库和上传目录可写性，但还缺少数据库文件大小、上传目录大小、最近备份信息等运维判断字段。
5. 文档描述了更新流程，但缺少“失败时如何回滚、如何确认备份可用、如何比对上线前后版本”的操作手册。

满分 100 分，分数越高越优先。

## 5. P0 任务细化

### P0-1：新增回滚脚本

目标：部署后发现健康检查失败、页面异常、服务无法启动时，可以快速回滚代码并重启服务。

建议能力：

- 默认回滚到 `HEAD@{1}` 或部署前记录的 commit。
- 支持显式传入 commit：`bash scripts/rollback.sh 9263f08`。
- 回滚前自动创建数据安全备份。
- 回滚后重启 `gokottamaker`。
- 回滚后请求 `/healthz` 并输出版本、build、gitCommit。
- 不自动删除运行数据，避免误伤 SQLite 和上传图片。

建议评分：96  
原因：当前上线流程已经进入真实服务器阶段，缺少脚本化回滚会让每次发布都有不可控恢复成本。

### P0-2：备份校验机制

目标：让备份从“复制过了”升级为“确认可恢复”。

建议能力：

- 备份后生成 `manifest.txt` 或 `manifest.json`。
- 记录备份时间、源目录、目标目录、数据库文件大小、上传文件数量。
- 对 SQLite 主库执行 `PRAGMA integrity_check`。
- 生成核心文件 sha256。
- 恢复脚本恢复前读取 manifest 并确认备份结构完整。
- 恢复后再次检查数据库完整性。

建议评分：94  
原因：项目真实数据集中在 SQLite 与 uploads，一旦备份不可用，管理端内容和图片会同时丢失。

### P0-3：部署前后版本比对

目标：每次执行 `deploy-update.sh` 后都能明确回答“从哪个版本更新到了哪个版本，服务是否真的跑在新版本上”。

建议能力：

- 部署前记录：
  - 当前 git commit
  - `server.js` 中 `siteVersion/siteBuild`
  - `/healthz` 返回的 `versionLabel/gitCommit`
  - systemd 服务状态
- 部署后记录：
  - 新 git commit
  - 新 `versionLabel`
  - `/healthz` 返回值
  - `systemctl is-active`
- 输出差异摘要。
- 如果代码 commit 更新但 `/healthz.gitCommit` 未变化，提示服务可能未重启成功。

建议评分：92  
原因：当前已经修过“静态资源缓存更新不可见”等问题，版本比对能快速定位“代码已更新但线上未生效”的情况。

### P0-4：失败路径提示

目标：让部署脚本失败时直接给出下一步，而不是只中断。

建议能力：

- 在 `git pull`、`systemctl restart`、`curl /healthz` 失败时输出：
  - 当前 commit
  - 最近备份目录
  - 推荐回滚命令
  - 查看日志命令：`sudo journalctl -u gokottamaker -n 120 --no-pager`
- 可选：提供 `ROLLBACK_ON_FAILURE=true` 时自动回滚。

建议评分：90  
原因：失败恢复路径应该跟部署脚本绑定，避免人在高压状态下翻文档。

## 8. 当前风险提示

1. 当前工作区状态为 `main...origin/main [ahead 1]`，本地比远端领先 1 个提交。执行线上部署前需要确认远端是否已经包含 `57956be`。
2. 当前 `backup-linux.sh` 会清理超过保留天数的备份目录，但没有保底保留最近 N 份，极端情况下可能清理过多。
3. 当前 `restore-linux.sh` 使用 `rm -rf` 替换目标目录中的 `database` 和 `uploads`，应先完成备份结构校验和 dry-run，降低误操作风险。
4. 当前版本信息分散在 `server.js` 和 `data/site-meta.js`，后续发布容易漏同步。
5. 当前 `/healthz` 能确认服务存活和基本状态，但不足以独立判断数据体积、备份状态和上线前后差异。
